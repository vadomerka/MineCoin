# Отчёт: MineCoin

## 1. Доменная область

MineCoin — веб-приложение с аккаунтами пользователей и внутренней игровой валютой **MineCoin (MNC)**. Реальные деньги не участвуют, источник монет — кнопка «Пополнить», но финансовая логика сделана так же строго, как для настоящих денег.

Что может пользователь:
- зарегистрироваться, войти по логину и паролю, посмотреть и изменить свой профиль, удалить аккаунт;
- пополнить кошелёк и снять с него монеты (не больше 1000 MNC за операцию);
- перевести монеты другому пользователю по логину;
- посмотреть историю своих операций с направлением (входящая / исходящая) и второй стороной перевода.

Кошелёк создаётся автоматически при первом обращении. Администратор (роль `ADMIN`) может просматривать, изменять и удалять любых пользователей через API.

**Гарантии:**
- баланс никогда не уходит в минус — проверка в домене и `CHECK (balance >= 0)` в базе;
- перевод атомарен — списание, зачисление и запись операции выполняются в одной транзакции БД;
- параллельные операции не теряют обновлений — кошельки блокируются `SELECT … FOR UPDATE`, при переводе оба кошелька блокируются одним запросом в порядке `id`, поэтому встречные переводы не попадают в дедлок;
- история операций неизменяема — записи только создаются;
- удаление аккаунта анонимизирует персональные данные (логин, email, имя, хеш пароля), а логин и email освобождаются для новой регистрации.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Бэкенд | Java 25, Spring Boot 4.0 (Web MVC, Data JPA, Validation, Security, OAuth2 Resource Server, Actuator), Hibernate 7, Flyway, springdoc-openapi (Swagger UI), Lombok |
| Аутентификация | JWT, подпись HS256 общим секретом; токены выпускает `user-service`, оба сервиса проверяют подпись сами |
| База данных | PostgreSQL 17, отдельная база и пользователь на каждый сервис |
| Фронтенд | HTML, CSS, JavaScript (ES-модули, `fetch`) без сборки; Pico CSS 2.1.1 |
| API gateway | nginx 1.28: раздача статики и маршрутизация `/api/*` в сервисы |
| Тесты | JUnit 6, AssertJ, Mockito, Testcontainers (PostgreSQL), ArchUnit, `MockRestServiceServer` |
| Сборка и запуск | Maven (многомодульный проект, Maven Wrapper 3.9.12), Docker (многоэтапные образы), Docker Compose |

```mermaid
Браузер --> Frontend (nginx Api gateway)

    - "/api/wallets" --> F[finance-service]
        - База данных finance-service --> U[user-service]
        
    - "/api/auth, /api/users" --> U[user-service]
        - База данных user-service
```

Оба сервиса устроены одинаково, в три слоя: `domain` (сущности и бизнес-правила), `service` (сценарии использования и репозитории), `infrastructure` (REST-контроллеры, безопасность, HTTP-клиент, конфигурация). Зависимости направлены только внутрь (`infrastructure` → `service` → `domain`), это проверяет тест ArchUnit в каждом сервисе.

`finance-service` хранит только идентификаторы пользователей. Логин получателя при переводе и логины в истории он запрашивает у `user-service` по HTTP, пробрасывая токен пользователя. Если `user-service` недоступен, баланс, пополнение, снятие и история продолжают работать (история — без логинов), отказывают только переводы (ответ `503`).

## 3. Основные сущности

### `users` (user-service, база `users_db`) — полный CRUD

| Поле | Тип | Примечание |
|---|---|---|
| `id` | UUID | первичный ключ |
| `username` | VARCHAR(32) | уникален без учёта регистра; по нему переводят монеты |
| `email` | VARCHAR(255) | уникален без учёта регистра |
| `password_hash` | VARCHAR(100) | BCrypt |
| `display_name` | VARCHAR(64) | необязательно |
| `role` | `USER` / `ADMIN` | |
| `status` | `ACTIVE` / `BLOCKED` / `DELETED` | удаление мягкое, с анонимизацией |
| `created_at`, `updated_at` | TIMESTAMPTZ | |

Операции: регистрация (create), просмотр профиля и списка пользователей (read), изменение профиля (update), удаление аккаунта (delete).

### `wallets` (finance-service, база `finance_db`) — кошелёк

| Поле | Тип | Примечание |
|---|---|---|
| `id` | UUID | первичный ключ |
| `user_id` | UUID | `UNIQUE` — один кошелёк на пользователя |
| `balance` | BIGINT | `CHECK (balance >= 0)`, только целые монеты |
| `created_at`, `updated_at` | TIMESTAMPTZ | |

Операции: создание при первом обращении (`INSERT … ON CONFLICT DO NOTHING`), чтение, изменение баланса через пополнение, снятие и перевод.

### `operations` (finance-service) — неизменяемая история

| Поле | Тип | Примечание |
|---|---|---|
| `id` | UUID | первичный ключ |
| `type` | `DEPOSIT` / `WITHDRAW` / `TRANSFER` | |
| `from_wallet_id` | UUID | `NULL` для пополнения |
| `to_wallet_id` | UUID | `NULL` для снятия |
| `amount` | BIGINT | `CHECK (amount > 0)` |
| `created_at` | TIMESTAMPTZ | |

`CHECK`-ограничение проверяет согласованность типа и сторон: у пополнения есть только получатель, у снятия — только отправитель, у перевода — оба и разные. Операции только создаются и читаются.

### Основные эндпоинты

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/auth/register`, `POST /api/auth/login` | все | регистрация, вход → JWT |
| `GET / PUT / DELETE /api/users/me` | вошедший | свой профиль |
| `GET /api/users`, `GET / PUT / DELETE /api/users/{id}` | `ADMIN` | управление пользователями |
| `GET /api/users/lookup`, `GET /api/users/names` | вошедший | поиск по логину и логины по id (для `finance-service`) |
| `GET /api/wallets/me` | вошедший | баланс |
| `POST /api/wallets/me/deposit`, `/withdraw`, `/transfer` | вошедший | операции |
| `GET /api/wallets/me/operations` | вошедший | история |
| `GET /api/wallets/limits` | вошедший | лимит операции |

Ошибки возвращаются в формате `ProblemDetail` (RFC 9457) с машинно-читаемым полем `code` (`INSUFFICIENT_FUNDS`, `USERNAME_TAKEN` и т. д.), по которому фронтенд выбирает текст сообщения.

## 4. Соответствие 12 факторам

### I. Кодовая база

Один git-репозиторий, из которого собираются три развёртываемых образа: `minecoin/user-service`, `minecoin/finance-service`, `minecoin/frontend`. Окружения (разработка, stage, production) — это развёртывания одной и той же кодовой базы, отличающиеся только env-файлом. Общего кода между сервисами нет: каждый собирается и деплоится независимо.

### II. Зависимости

- Все Java-зависимости объявлены в [`pom.xml`](pom.xml) и `*/pom.xml`. Версии зафиксированы BOM Spring Boot 4.0.8 (Spring 7.0.9, Hibernate 7.2.24, Flyway 11.14.1, драйвер PostgreSQL 42.7.13, Jackson 3.1.5) и явно указанными версиями springdoc 3.0.3, ArchUnit 1.5.1, Testcontainers 2.0.5.
- Maven Wrapper ([`mvnw`](mvnw), [`.mvn/wrapper/maven-wrapper.properties`](.mvn/wrapper/maven-wrapper.properties)) фиксирует Maven 3.9.12 — для сборки достаточно JDK.
- Базовые образы закреплены по версиям: `eclipse-temurin:25-jdk-alpine` / `25-jre-alpine`, `nginx:1.28-alpine`, `postgres:17-alpine`.
- Фронтенд не имеет менеджера пакетов: единственная внешняя зависимость, Pico CSS, лежит в репозитории с версией в имени файла (`pico-2.1.1.min.css`) и не загружается с CDN во время работы.
- Изоляция: сборка и запуск происходят в Docker-образах, от системы нужен только Docker. Неявных системных зависимостей нет — healthcheck использует `wget`, встроенный в Alpine.

### III. Конфигурация

- Всё, что отличается между окружениями, задаётся переменными окружения: адреса и учётные данные баз, адрес `user-service` для `finance-service`, секрет и срок жизни JWT, порты, лимит операции, формат логов, тег образов, данные администратора. Полный перечень — [`.env.example`](.env.example).
- В `application.yml` только плейсхолдеры (`${DB_URL}`, `${JWT_SECRET}`); значения по умолчанию есть лишь у безопасных параметров (порт, TTL, лимит).
- У секретов значений по умолчанию нет. Compose требует `JWT_SECRET` явно (`${JWT_SECRET:?JWT_SECRET is required}`), а приложение при старте проверяет, что секрет не короче 32 байт, — иначе отказывается запускаться.
- `.env` и локальные env-файлы в `.gitignore`, в репозитории только пример.
- Фронтенд не содержит адреса API: он обращается к относительному пути `/api`, а куда проксировать запросы, nginx узнаёт из переменных `USER_SERVICE_UPSTREAM` и `FINANCE_SERVICE_UPSTREAM` при старте ([`default.conf.template`](Frontend/nginx/default.conf.template)). Один и тот же образ фронтенда работает в любом окружении.

### IV. Сторонние службы

- PostgreSQL подключается по строке из env (`USER_DB_URL`, `FINANCE_DB_URL`). Замена локального контейнера на управляемый облачный PostgreSQL — правка env-файла без изменения кода.
- Каждый сервис ходит только в свою базу под своим пользователем ([`infra/postgres/init/01-init.sh`](infra/postgres/init/01-init.sh)): в разработке это один контейнер, но логически два независимых ресурса.
- Для `finance-service` сервис `user-service` — тоже подключаемый ресурс: адрес задаётся `USER_SERVICE_URL`, доступ идёт через интерфейс `UserDirectory`, реализация `HttpUserDirectory` имеет таймауты (подключение 2 с, чтение 3 с) и переводит сбои в понятную ошибку `503 USER_SERVICE_UNAVAILABLE`.

### V. Сборка, релиз, выполнение

- **Сборка:** многоэтапные Dockerfile ([`UserService/Dockerfile`](UserService/Dockerfile), [`FinanceService/Dockerfile`](FinanceService/Dockerfile), [`Frontend/Dockerfile`](Frontend/Dockerfile)) собирают образы без конфигурации окружения. Тег образа — короткий git SHA: `IMAGE_TAG=$(git rev-parse --short HEAD) docker compose build`.
- **Релиз:** неизменяемая связка «тег образов + env-файл окружения» (например, `.env.stage` с `IMAGE_TAG=<sha>`). Идентификатор релиза — SHA коммита.
- **Выполнение:** `docker compose -f docker-compose.yml --env-file .env.stage up -d --no-build --wait` запускает уже собранные образы без пересборки. Один и тот же образ переносится между окружениями, меняется только env.

### VI. Процессы

- Сервисы не хранят состояние в памяти: сессий нет (JWT передаётся в заголовке и проверяется по подписи), всё состояние — в PostgreSQL.
- Создание кошелька идемпотентно (`INSERT … ON CONFLICT DO NOTHING` + `UNIQUE(user_id)`), поэтому одновременные первые запросы одного пользователя к разным экземплярам не создают дубликатов.
- Фронтенд — статические файлы; состояние пользователя (токен) хранится в браузере.
- Процесс можно перезапустить в любой момент без потери данных — проверено остановкой экземпляра под нагрузкой (фактор IX).

### VII. Привязка портов

- Каждый Java-сервис — самостоятельный HTTP-сервер со встроенным Tomcat; порт задаётся переменной `SERVER_PORT`.
- `frontend` — nginx на порту 80, наружу публикуется как `FRONTEND_PORT`.
- Сервисы доступны друг другу по имени в сети Compose (`http://user-service:<порт>`).
- В режиме «как в продакшене» (`docker compose -f docker-compose.yml up`) наружу опубликован только `frontend`; порты сервисов и PostgreSQL для разработки вынесены в [`docker-compose.override.yml`](docker-compose.override.yml), который Compose подключает автоматически только при обычном `docker compose up`.

### VIII. Параллелизм

Масштабирование — запуском нескольких одинаковых процессов:
```bash
docker compose -f docker-compose.yml up -d --wait --scale user-service=2 --scale finance-service=2
```
- nginx переразрешает DNS-имена сервисов (`resolver 127.0.0.11 valid=10s`, `upstream … resolve`) и сам находит новые экземпляры; распределение запросов видно в access-логе (`upstream=<адрес экземпляра>`).
- Корректность обеспечивают блокировки строк в базе, а не память процесса.
- Миграции выполняет отдельный разовый процесс, а не каждый экземпляр.

Проверено через gateway на двух экземплярах каждого сервиса:

| Сценарий | Результат |
|---|---|
| 20 параллельных снятий по 50 с баланса 500 | ровно 10 успешных (`200`), 10 отказов `422 INSUFFICIENT_FUNDS`, итоговый баланс 0 |
| 30 параллельных переводов по 50 с баланса 1000 | ровно 20 успешных, 10 отказов; у отправителя 0, у получателя 1000 |
| распределение запросов к `finance-service` | 28 и 27 запросов на два экземпляра |
| миграции | `user-migrate` и `finance-migrate` выполнились по одному разу |

Те же гарантии закреплены автотестами (`WalletServiceIT`): 20 параллельных снятий не уводят баланс в минус, 50 встречных переводов A↔B проходят без дедлока. Для контроля тест прогонялся с отключённой блокировкой — тогда все 20 снятий по 10 с баланса 100 «успешны», то есть 200 монет выводятся из ниоткуда; с блокировкой ошибка исчезает.

### IX. Утилизируемость

- **Быстрый старт:** сервисы стартуют за ~8 с, процессы миграций — за 6–7 с, nginx — менее чем за секунду. Миграции вынесены из старта сервисов.
- **Корректная остановка по SIGTERM:** `server.shutdown: graceful`, `spring.lifecycle.timeout-per-shutdown-phase: 20s`, в Compose `stop_grace_period: 30s`; процесс Java — PID 1 (exec-форма `ENTRYPOINT`) и сам получает сигнал.
- **Проверено под нагрузкой:** два экземпляра `finance-service`, 8 параллельных потоков запросов (чтение баланса и пополнения) в течение 20 с, посередине один экземпляр остановлен `docker stop`. Результат — 1152 запроса, все `200`; баланс вырос ровно на число успешных пополнений (576), ни одно не потеряно и не задвоено; остановка заняла 1,3 с, в логах `Commencing graceful shutdown. Waiting for active requests to complete` → `Graceful shutdown complete`, код выхода 143.
- **Устойчивость к внезапным падениям:** каждая денежная операция — одна транзакция БД, частично выполненных операций не бывает. При недоступном сервисе nginx отвечает за 3 с (`proxy_connect_timeout`), а не зависает; после перезапуска контейнера с новым IP nginx переключается на него без собственного перезапуска.
- Health-пробы Actuator `liveness` и `readiness` используются в healthcheck Compose.

### X. Паритет разработки и продакшена

- Один и тот же [`docker-compose.yml`](docker-compose.yml) и одни и те же образы во всех окружениях; различия — только в env-файле. Файл override для разработки лишь публикует дополнительные порты и не меняет поведение.
- Везде используется PostgreSQL 17 — без H2 и in-memory заменителей. Интеграционные тесты поднимают тот же образ `postgres:17-alpine` через Testcontainers и применяют те же миграции Flyway.
- Схема базы создаётся только миграциями Flyway; Hibernate работает в режиме `validate` и проверяет соответствие сущностей таблицам при старте.

### XI. Журналирование

- Все процессы пишут логи только в stdout как поток событий; файлов логов нет. Хранение и анализ — забота окружения (`docker compose logs`, в перспективе Loki или ELK).
- В Docker логи сервисов структурированные — JSON в формате ECS (переменная `LOG_FORMAT`, по умолчанию `ecs`): каждая строка содержит `@timestamp`, уровень, логгер, `service.name` и сообщение, поэтому в общем потоке видно, какой сервис её записал. При запуске из IDE логи остаются обычным текстом.
- Access-лог nginx содержит адрес экземпляра, обработавшего запрос, время ответа и идентификатор запроса (`X-Request-Id`, он же возвращается клиенту в заголовке ответа).
- Пароли и токены в логи не пишутся.

### XII. Задачи администрирования

Разовые задачи выполняются отдельными одноразовыми процессами того же образа, с тем же кодом, той же конфигурацией (общие YAML-якоря `x-user-env` и `x-finance-env` в Compose) и теми же зависимостями:
- **миграции БД** — сервисы `user-migrate` и `finance-migrate`: то же приложение с `FLYWAY_ENABLED=true` и без веб-сервера; применяет миграции и завершается. Сервисы стартуют только после их успешного завершения (`service_completed_successfully`);
- **создание первого администратора** — `docker compose --profile tools run --rm user-create-admin` ([`CreateAdminCommand`](UserService/src/main/java/com/minecoin/user/infrastructure/command/CreateAdminCommand.java)): регистрирует пользователя с ролью `ADMIN` или повышает существующего. Команда идемпотентна, без SQL-скриптов с захардкоженным хешем пароля.

## 5. Известные ограничения

- JWT нельзя отозвать до истечения срока (`JWT_TTL`, по умолчанию 1 час): выход — это удаление токена в браузере; смена роли или блокировка начинают действовать после нового входа. Удалённый пользователь со старым токеном получает `404` на свои эндпоинты.
- Нет refresh-токенов: по истечении срока пользователь входит заново.
- Переводы зависят от доступности `user-service` (поиск получателя по логину). Развитие — события Kafka и локальная копия логинов в `finance-service`; точки расширения уже заложены (идемпотентный `openWallet` и интерфейс `UserDirectory`).
- Нет защиты от повторной отправки запроса (ключа идемпотентности): двойной клик по «Пополнить» создаст две операции.
- Деньги на кошельке удалённого пользователя остаются в базе, но становятся недоступны.
- Нет интерфейса администратора (только API) и блокировки пользователей через API.
- Приложение работает по HTTP; в продакшене TLS завершается на внешнем балансировщике или nginx.

## 6. Как проверить

Инструкция запуска — в [README.md](README.md). Основной сценарий: `cp .env.example .env` → заменить `JWT_SECRET` → `docker compose up --build -d --wait` → `docker compose --profile tools run --rm user-create-admin` → открыть http://localhost:8080 → зарегистрировать двух пользователей → пополнение, снятие, перевод → история у обоих → изменение и удаление профиля.

Автотесты (`./mvnw verify`, нужен Docker): 56 тестов — модульные тесты домена, проверки архитектуры ArchUnit, интеграционные тесты HTTP API обоих сервисов на настоящем PostgreSQL, тесты конкурентности переводов и снятий, тест HTTP-клиента между сервисами.
